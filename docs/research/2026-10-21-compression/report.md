# Реальное частичное сжатие clean1000

Проверено 21 октября 2026 на Apple M5, CPUExecutionProvider, два потока,
ONNX Runtime 1.19.2. Исходная модель: 10 блоков Qwen3, hidden 256,
MLP 1024, 4 query / 2 KV heads, 14 957 568 уникальных параметров.
SHA-256 исходного ONNX:
`6f27137365b90aaa97a3992a6ada4a060916a88e4742423a4b5b4424f7bebb76`.

Получен настоящий уменьшенный ONNX: **MLP 1024 → 896**, **−6,57% параметров**,
с сохранением всех attention-блоков. Вместе с устранением дублированной tied
матрицы файл сокращается **76,81 → 53,52 МиБ (−30,31%)**. На дополнительном
наборе из 80 английских задач результат **59/80 против 63/80** у исходной
модели. Это измеримый компромисс качества, а не гарантия его сохранения.
Профиль проверен через текущий LanguageEngine: настоящая токенизация,
attention, генерация `red cup` и восстановление при обучении работают.

Это исследовательские артефакты. Production checkpoint и выбор профиля по
пользовательскому графу в рамках исследования не менялись.

## Какой способ оказался пригодным

Внутри каждого SwiGLU MLP вычисляется `z = SiLU(gate(x)) * up(x)`. Для каждого
канала измеряется `Var(z_j) * ||W_down[:, j]||²` на 4784 calibration-токенах.
Оставляются 896 наиболее значимых каналов: физически удаляются строки
gate/up и столбцы down. Размеры матриц действительно меняются; нулевые маски
не используются.

Оставшаяся down projection восстанавливается решением небольшой задачи
линейной алгебры:

`min_D ||Z_keep Dᵀ − Z_full W_downᵀ||² + λ ||D − W_down_keep||²`.

`λ = 0.001 * mean(diag(Z_keepᵀ Z_keep))`. Эмбеддинги, hidden size, RoPE,
attention weights и головы остаются исходными. Обратного распространения и
оптимизатора нет. Это адаптация идеи structured pruning и компенсации из
[FLAP](https://arxiv.org/html/2312.11983v1), с равномерной шириной и собственной
ridge-реконструкцией; полный алгоритм FLAP с глобальным поиском не воспроизводился.

Первый вариант ridge добавлял bias. Он немного лучше на задачах, но текущий
trace adapter ошибочно определяет дополнительные Add как выходы блоков.
Вариант **без bias** сохраняет совместимость, поэтому дальнейшая проверка
проведена именно с ним. Никаких фиктивных attention-карт для обхода этой
несовместимости не создавалось.

## Проверка качества

Использован правильный ChatML из kit и английские данные исходного комплекта:
арифметика, копирование/преобразование текста, разряды, извлечение фактов,
история диалога, reasoning и простые знания.

- Calibration: 60 примеров из train, 4784 полных токена.
- Validation: 20 примеров, контроль удаления блоков и выбор варианта реконструкции.
- Первый test: 40 примеров; по четыре на каждую из десяти категорий.
- Дополнительный test: 80 новых примеров, исключены все 120 предыдущих
  `group_id`. Эти 80 примеров не использовались для подбора коэффициентов.

Арифметика оценивается по финальному целому ответу; промежуточные рассуждения
отдельно не проверяются. Текст — по нормализованному совпадению, факты — по
ожидаемым терминам. Такой grader может отвергать допустимые перефразирования
и недостаточен для общего заявления о сохранении способностей.
Assistant-only NLL и согласие с исходной моделью считаются отдельно.
Это **не процент accuracy, показываемый учебным графиком Neuralese**.

### Дополнительные 80 задач

| Вариант | Параметры | Решено | Assistant NLL | Совпадение top-1 с исходной | Совместим с текущим trace |
|---|---:|---:|---:|---:|---|
| Исходный | 14 957 568 | 63/80 | 1,1552 | 100% | Да |
| MLP 896, ridge с bias | 13 977 088 | 60/80 | 1,1773 | 97,35% | Нет |
| MLP 896, ridge без bias | 13 974 528 | 59/80 | 1,1768 | 97,27% | Да |
| MLP 960, ridge без bias | 14 466 048 | 59/80 | 1,1670 | 98,44% | Да |

У MLP 896 без bias сохранены 58 из 63 исходно успешных случаев, потеряны
пять, приобретён один. Среди потерь есть настоящие ошибки арифметики:
`576 + 667` стало `1143` вместо `1243`; `90 − 30` стало `49` вместо `60`.
Поэтому высокое token agreement нельзя выдавать за сохранение всех навыков.

ONNX и PyTorch проверены на prefill 1/32/128 и cached decode по два токена.
Затем оба профиля ONNX отдельно прошли все 80 задач: результаты совпали с
таблицей. Для всех 10×4 attention heads проверены форма, конечность значений,
сумма вероятностей 1 и causal mask. Через текущий runtime на ONNX 1.14.1
проверены preview, генерация и training_step с progress 0/1; agreement меняется
0 → 1 относительно учителя этого профиля. Torch/Transformers не импортируются.

### Почему не удалять блоки или усреднять их веса

Проверена последовательная оценка каждого удаления по calibration NLL,
с повторным расчётом после удаления — принцип
[SLEB](https://arxiv.org/html/2402.09025v1). В отличие от прежнего резкого
сжатия до 2/4/6 блоков, здесь проверялись мягкие 10→9→8.

| Вариант | Решено из 40 | Test NLL |
|---|---:|---:|
| Исходный, 10 блоков | 26 | 0,9702 |
| 9 блоков, удалён последний | 20 | 0,9120 |
| 8 блоков, удалены исходные 9 и 3 | 3 | 2,2717 |
| Лучшее соседнее усреднение 0,5/0,5, 9 блоков | 0 | 2,3877 |
| MLP 768, ridge с bias | 20 | 1,0074 |
| MLP 512, ridge с bias | 10 | 1,2042 |

Индексы блоков в таблице с нуля. Усреднение служило отрицательным контролем;
это не полная реализация LaCo. Однократный cosine BI из
[ShortGPT](https://aclanthology.org/2025.findings-acl.1035/) не является
гарантией безопасного удаления: небольшое локальное изменение может быть
важно для продолжения генерации. На нашем маленьком checkpoint простое
сокращение глубины работает хуже мягкого сокращения MLP.

Показательный результат: удаление последнего блока **улучшило NLL**, но число
правильных ответов снизилось с 26 до 20. Выбирать архитектуру только по loss
для этого продукта неправильно.

## Сжатие файла и квантизация

В исходном ONNX embedding `[20002,256]` и output matrix `[256,20002] содержат
одни и те же tied weights в разном порядке. Точное равенство проверено.
Замена второй матрицы Transpose первой даёт −25,43% файла, нулевой KL,
100% top-1 agreement и прежние ответы. Число нейронов и арифметических
операций при этом не уменьшается. Снижение RSS не измерялось: ORT может
снова материализовать transpose при оптимизации.

По [официальному механизму ORT](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)
проверены per-channel dynamic INT8 и weight-only MatMulNBits INT4
(block 32, symmetric, accuracy level 0). Это offline-преобразования,
не дополнительные зависимости приложения.

| Вариант | Файл, МиБ | Решено /40 | NLL | Decode 32 токена, мс | Текущий trace |
|---|---:|---:|---:|---:|---|
| FP32 | 76,81 | 26 | 0,9702 | 37,72 | Да |
| FP32, tied matrix без дубликата | 57,27 | 26 | 0,9702 | 37,74 | Да |
| INT8 MatMul | 34,44 | 22 | 1,4530 | 19,67 | Да |
| INT8 MatMul + Gather | 19,79 | 25 | 1,4755 | 19,60 | Нет |
| INT4 MatMul | 28,70 | 23 | 1,0424 | 149,23 | Да |

INT8 ускорил decode на этом M5, но заметно изменил распределения. INT4 дал
меньший файл, однако оказался примерно в четыре раза медленнее в выбранном
ORT ARM kernel. На Windows x64 эти замеры нужно повторять.
Gather INT8 требует корректно извлекать dequantized embeddings: текущий
adapter ошибочно объявляет uint8 Gather как float. Такой профиль нельзя
просто включить в приложение.

Для каждого замера выполнены прогрев, несколько повторов, одинаковые длины
prefill 32/128 и ровно 32 cached decode-токена. Ранний EOS не сокращает работу.
Подробные median/p95 находятся в JSON. Мягкое уменьшение MLP даёт небольшое
ускорение, порядка нескольких процентов; уменьшение файла на 30% не означает
ускорения на 30%.

## Практический вариант для дальнейшей интеграции

При нулевом допустимом изменении качества можно применить только удаление
дубликата tied matrix. При допустимой небольшой потере качества есть
проверенный физический MLP-профиль 896, совместимый с текущими визуализациями
и восстановлением обучения. Для близкой к исходной пользовательской сети
нужно сохранять исходный профиль.

Варианты лучше готовить offline и отдавать приложению как ONNX/небольшие
patch-assets с source hash, индексами каналов и пересчитанными down weights.
Тогда на компьютере ребёнка не нужны Torch, Transformers или реальная
оптимизация весов. Сопоставление пользовательской архитектуры с этими
профилями требует отдельной интеграции и более широкого quality gate.
Сохранение качества при двух физических блоках пока не подтверждено.

команд из корня репозитория (KIT — исходный kit, CACHE — отдельный каталог
производных артефактов):

```bash
export PYTHONPATH=local_runtime:.
python -m tools.language_models.compression_study --kit "$KIT" --cache "$CACHE/candidates" --report docs/research/2026-10-21-compression/results.json
python -m tools.language_models.compression_onnx_probe --kit "$KIT" --candidates "$CACHE/candidates" --cache "$CACHE/onnx" --study docs/research/2026-10-21-compression/results.json --report docs/research/2026-10-21-compression/onnx-results.json
python -m tools.language_models.compression_biasless_probe --kit "$KIT" --candidates "$CACHE/candidates" --cache "$CACHE/biasless" --study docs/research/2026-10-21-compression/results.json --report docs/research/2026-10-21-compression/biasless-results.json
python -m pytest tests/language_models/test_compression_research.py -q
```

Последняя совместимость отдельно проверяется **интерпретатором runtime**:

```bash
<runtime-python> tools/language_models/probe_compressed_runtime.py --model-root "$CACHE/biasless/mlp_896_ridge_no_bias" --report docs/research/2026-10-21-compression/biasless-results.json
```

Исходный kit не перезаписывался, его ONNX hash проверен после экспериментов.
Производные `.pt`/ONNX хранятся в research cache и в Git не добавлялись.
