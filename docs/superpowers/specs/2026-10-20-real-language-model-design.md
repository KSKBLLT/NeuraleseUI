## Цель

Ребёнок собирает языковую сеть из существующих нод, вводит текст и видит настоящую токенизацию, векторы слов, внимание и вероятности локальной модели. Подготовка использует готовые веса вместо обучения с нуля. Изменения архитектуры приблизительно отражаются в модели; качество важнее буквального совпадения всех размеров.

## Выбранная архитектура

Godot использует существующую асинхронную границу `LanguageBackend`. Новый backend обращается к резидентному локальному Python worker. Модель и tokenizer загружаются один раз; каждая сессия имеет собственные prefix IDs, generated IDs, RNG и KV-cache. Runtime использует NumPy, tokenizers и ONNX Runtime. PyTorch остаётся инструментом подготовки и эталонных тестов.

Базовый ONNX сохраняется. Отдельная инструментированная копия публикует настоящие embeddings, выходы блоков, attention probabilities и выходы голов. Метаданные связывают каждый выход с физическим слоем и головой. Проверяется равенство logits инструментированной и исходной моделей. Карты внимания получаются из того же forward pass, который даёт показанные вероятности.

Существующие методы `capabilities`, `open_session`, `tokenize`, `run_step`, `inspect`, `vocabulary_page`, `cancel`, `close_session` сохраняются. Добавляется `preview_node`: вычисляет данные принимающего нода без выбора следующего токена. Ответ несёт `request_id`, `session_id`, `graph_revision`, `provider_id`, `is_dummy=false`, идентификатор модели и фактическое сопоставление нод.

Worker использует существующий подход локального runtime: процесс + атомарные JSON-файлы, очередь с монотонными ID, stop-файл и наблюдение за родительским процессом. Тяжёлые полные трассы не передаются каждый кадр. `inspect` получает нужную голову/диапазон; обычный ответ ограничен видимыми данными.

## Адаптация пользовательского графа

Сначала канонизировать языковой DAG: отделить источники, блоки внимания, параллельные головы, Concat, внутренние Dense и финальную проекцию словаря. Числовые ветки не переводить в языковой runtime. Параллельные головы одного этапа не считать четырьмя последовательными блоками. Связь нода с физическим слоем выводить из топологии, а не случайного graph ID.

При числе этапов 8–12 использовать исходные десять блоков и сопоставление визуальных этапов. Веса остаются побитово исходными. При меньшем числе этапов сравнить BI-pruning, слияние соседних блоков LERP/SLERP и неизменную модель с группировкой блоков. SLERP — экспериментальный кандидат; он не гарантирует сохранения функции последовательных слоёв.

Подготовка профилей выполняется один раз и кэшируется по хешу исходных весов, топологии и версии алгоритма. Проверочные тексты отделены от калибровочных. Для автоматического выбора сжатого профиля: NLL не более 1.2× исходного, согласие greedy top-1 не менее 0.8, точность сохранённых задач не менее 0.95× исходной. Если профиль не проходит, использовать более близкий качественный профиль/исходные блоки, сгруппированные в визуальные этапы. Сохранять фактическую глубину и сопоставление, не объявлять десять физических слоёв двумя.

Ширина 256, RoPE, GQA, RMSNorm, tokenizer, словарь и tied weights по умолчанию сохраняются. Число нейронов в UI приблизительно сопоставляется с этапами; произвольные 64/128/8192 не являются поводом обрезать матрицы checkpoint. Финальная проекция всегда даёт 20 002 logits. Некорректная/циклическая сеть получает понятную ошибку. Неполная сеть может показывать промежуточные данные до подключённого этапа.

Источники подходов: [ShortGPT/ShortGPT-gen](https://aclanthology.org/2025.findings-acl.1035/), [LaCo](https://aclanthology.org/2024.findings-emnlp.372/), [SliceGPT](https://arxiv.org/abs/2401.15024). Выбор для Neuralese определяется экспериментом на clean1000; результаты больших моделей автоматически не переносятся на 15M checkpoint.

## Слова и геометрия эмбеддинга

Tokenizer показывает реальные token IDs и offsets. В Embedding одна точка соответствует слову. Сегментация Unicode поддерживает русский, казахский и английский; повторные появления слова сохраняют связь со своими позициями. Спецтокены ChatML не превращаются в видимые слова.

Сначала собрать один вектор слова из исходных 256-мерных embeddings его token IDs, затем проецировать. Offset-перекрытия byte-level токенов не должны давать одному символу больший вес. UI больше не усредняет уже нарисованные точки токенов и не подставляет вектор первого токена вместо вектора слова.

Проекция — одна фиксированная линейная матрица на checkpoint/язык, обученная на небольшом наборе смысловых отношений с регуляризацией к PCA и сохранению соседства. Для требуемых примеров ограничить разность проекций направлений «мама→папа» и «королева→король», контролировать длины и отсутствие схлопывания. Координаты не подставлять по названию слова. Детерминированные оси/масштаб не меняются при редактировании фразы. Сохранять матрицу, anchor-набор и метрики; tooltip честно называет это проекцией. На отдельных, не использованных при настройке аналогиях измерять обобщение. Теоретическая мотивация линейных отношений: [Analogies Explained](https://proceedings.mlr.press/v97/allen19a.html); конкретная настройка проекции — наше инженерное решение.

## Обновление при соединении

Уточнение пользователя: речь о **любых языковых нодах**.

Использовать событие принятой новой связи между языковыми нодами. После завершения операции связи запросить preview принимающего нода с его новым upstream. Это отдельная причина обновления, не сравнение fingerprint всего графа в каждом кадре. Добавление связи не должно генерировать токен, сбрасывать чужие трассы или прогонять сеть заново без необходимости.

Перемещение, выделение, масштабирование, добавление несвязанного нода, обычное редактирование графа и отключение связи не запускают такой preview. Отключение только инвалидирует зависимые данные/сессию. Ввод текста и явный «Шаг» остаются самостоятельными намеренными действиями. Undo удаления/redo добавления связи учитывают фактическое создание ребра; загрузка проекта выполняется в режиме подавления промежуточных preview. Запросы от старой ревизии/сессии игнорируются, включая offscreen-ноды.
