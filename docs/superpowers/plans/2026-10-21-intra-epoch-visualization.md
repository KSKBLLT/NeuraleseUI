# Промежуточные состояния обучения внутри эпох — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** При долгой эпохе регулярно показывать уже вычисленный прогресс и последние доступные реальные состояния модели, без дополнительных forward/backward, экспорта checkpoint и оценки validation ради анимации.

**Architecture:** Существующие batch-события и language snapshots — источники данных. Producer ограничивает частоту публикации, транспорт сохраняет только последний промежуточный пакет, UI применяет его не чаще 4 раз в секунду. Финальные события, ошибки и остановка доставляются обязательно. Короткие эпохи сохраняют прежнее поведение.

**Tech Stack:** Существующие Python 3.11/ONNX Runtime, mailbox языкового worker, протокол числового worker, Godot 4.7.1. Новых runtime-зависимостей нет.

**Spec:** Запрос пользователя от 21 октября 2026: показывать промежуточные состояния внутри долгих эпох, избегая ощущения остановки и лишней нагрузки. Реализация выполнена в текущей ветке; результаты и ограничения измерений — в `docs/research/2026-10-21-intra-epoch/report.md`. Уточнение пользователя: включать только при первой эпохе строго дольше 0,3 с.

## Что уже есть

- `scripts/language_models/language_training.gd`: 12 `training_step` на эпоху для встроенного текстового датасета; каждый ответ уже содержит реальные preview и метрики. UI обновляется после каждого ответа, а не только после эпохи. Если зависает один такой запрос, таймер сам по себе не создаст новое состояние модели.
- `local_runtime/neuralese_local/language/learning_session.py`: `training_preview` отдельно считает prompt preview, corpus metrics и agreement. Новый forward для каждого animation frame здесь недопустим.
- `local_runtime/neuralese_local/train_task.py`: числовое обучение уже отправляет `stage=batch`, `batch/batches`, `epoch` и `train_loss_so_far` после optimizer step.
- `scripts/train_begin.gd`: `_show_training_progress` заканчивается ранним `return`, поэтому подробности batch сейчас не доходят до отображения. Проценты в `train_input.gd` — accuracy, не доля выполненной эпохи.
- `scripts/language_models/local_language_worker.gd`: mailbox ответов; `scripts/local_training_worker.gd`: отдельный числовой transport. Их нельзя без проверки считать одним протоколом.

## Ограничения

- Абсолютно нулевого overhead у передачи и отрисовки нет. Цель: без новых вычислений модели, с ограниченными расходами; измеряемая добавка ко времени эпохи менее 1% на длинных контрольных прогонах. Если бюджет превышен — уменьшить частоту, а не увеличивать вычислительную нагрузку.
- Минимальный интервал промежуточных публикаций 250 мс; включение определяется первой эпохой: строго больше 0,3 с вычислений worker, без подготовки модели и задержек доставки UI. Классификация сохраняется до завершения данного обучения. Проверка времени — monotonic после существующего шага.
- Никакой полной vocabulary, checkpoint, ONNX-модели или копии всех активаций в промежуточном progress-пакете. Скалярные пакеты до 2 КиБ, UI-preview до 64 КиБ. Если реальный preview больше — передавать только подписанные видимые ноды или реже отправлять уже существующий полноценный snapshot.
- Только два preview-состояния в памяти UI: показанное и последнее ожидающее. Промежуточные обновления могут заменять друг друга; `done/error/stopped` терять нельзя.
- Истинные метрики хранятся без display-множителей. Запрошенный ×4 действует только на отображение accuracy ЛЛМ; это не progress эпохи.
- Не интерполировать метрики как будто они измерены. Плавный переход уже полученных визуальных кадров допустим только как эффект отрисовки; новая attention-матрица не объявляется вычисленной до настоящего ответа.

## Граница реализуемости

Для ЛЛМ можно раньше доставлять prompt preview, который уже считается в `training_preview`, и повторно использовать существующие batch snapshots. Для числовой модели, если training session не предоставляет промежуточные активации текущего пользовательского ввода, бесплатных реальных карт для этого ввода нет: показываем доступный batch progress и последнее полученное состояние. Дополнительный inference probe потребует отдельного согласованного вычислительного бюджета; он не входит в этот план «без дополнительных forward».

### Фактический охват

Headless worker и Godot проверены отдельно, включая реальные применения preview. Видимый GPU UI и запись видео требуют разблокировки Mac; эти пункты остаются открыты. Показ активности при одном атомарном вызове не меняет измеренные метрики или матрицы. Существующие числовые batch-события используются без дополнительного inference; стоимость числового ORT Training на этой macOS не измерялась.
